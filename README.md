# WorkTime — Учёт рабочего времени сотрудников

Небольшое корпоративное веб-приложение для учёта рабочего времени сотрудников компании, разработанное с нуля в рамках тестового задания.

Приложение позволяет вести список сотрудников, запускать и останавливать таймер по текущим задачам в реальном времени, просматривать журнал записей и формировать сводные отчёты по каждому сотруднику за выбранный период с сохранением всех данных в PostgreSQL.

## 1. Цель проекта и основные функции

- **Панель обзора (`/`)**:
  - Суммарно отработанное время за сегодня.
  - Количество активных сотрудников и запущенных таймеров.
  - Виджет быстрого старта и список активных таймеров с живым секундомером `HH:MM:SS`.
  - Таблица последних записей времени и информативное пустое состояние (Empty State) при первом запуске.
- **Управление сотрудниками (`/employees`)**:
  - Добавление сотрудника (имя, должность, необязательный уникальный email).
  - Редактирование данных сотрудника.
  - Деактивация и повторная активация сотрудников с полным сохранением исторических записей времени.
  - Поиск по имени, должности или email и фильтрация по статусу активности.
- **Учёт времени и таймер (`/time-tracking`)**:
  - Выбор активного сотрудника, ввод описания задачи и запуск таймера («Начать работу»).
  - Отображение работающего секундомера в формате `HH:MM:SS` и кнопка «Остановить».
  - Сохранение активного таймера при перезагрузке страницы и перезапуске приложения.
  - Журнал всех записей времени с фильтрацией по сотруднику и диапазону дат.
- **Отчёты за период (`/reports`)**:
  - Выбор начальной и конечной даты периода, а также быстрые пресеты («Сегодня», «Последние 7 дней», «Последние 30 дней»).
  - Точный расчёт времени пересечения каждой записи с выбранным интервалом `[start, end)`.
  - Сводная таблица по сотрудникам (количество задач и общее время в формате `12 ч 35 мин`) + детализация по каждой задаче.
  - Информативное состояние `«За выбранный период записей нет»`, если за период нет данных.

## 4. Запуск через Docker Compose (рекомендуемый способ)

Для запуска всего комплекса (приложение Next.js + PostgreSQL 16) одной командой:

```bash
docker compose up --build -d
```

Что происходит при запуске:
1. Запускается контейнер `worktime-db` (`postgres:16-alpine`) с именованным томом `worktime_postgres_data`.
2. После прохождения `healthcheck` базы данных (`pg_isready`) стартует контейнер `worktime-web`.
3. Скрипт `docker-entrypoint.sh` автоматически применяет миграции (`prisma migrate deploy`) и запускает сервер Next.js на порту `3000`.
4. Приложение становится доступно по адресу: **http://localhost:3000** (эндпоинт проверки готовности: `http://localhost:3000/api/health`).

### Сохранение данных при перезапуске

- Остановка контейнеров **с сохранением всех данных** в базе:
  ```bash
  docker compose down
  ```
  При следующем `docker compose up` все сотрудники и записи времени останутся на месте.
- Полная остановка **с удалением тома базы данных** (все данные будут стёрты):
  ```bash
  docker compose down -v
  ```

1. Скопируйте файл переменных окружения:

   ```bash

   ```

   ```bash
   npm ci
   ```

4. Сгенерируйте клиент Prisma и примените миграции:
   ```bash
   npx prisma generate
   npx prisma migrate deploy
   ```
5. Запустите сервер разработки:
   ```bash
   npm run dev
   ```
   Приложение откроется на **http://localhost:3000**.

## 10. Модель данных

- **`Employee` (Сотрудник)**:
  - `id` (`UUID`, Primary Key)
  - `name` (`String`, обязательное)
  - `email` (`String?`, необязательное, `UNIQUE`)
  - `position` (`String?`, необязательное)
  - `isActive` (`Boolean`, по умолчанию `true`)
  - `createdAt`, `updatedAt` (`DateTime` в UTC)
- **`TimeEntry` (Запись времени)**:
  - `id` (`UUID`, Primary Key)
  - `employeeId` (`String`, Foreign Key -> `Employee.id` с политикой `ON DELETE RESTRICT`)
  - `taskDescription` (`String`, обязательное)
  - `startTime` (`DateTime` в UTC, устанавливается сервером)
  - `endTime` (`DateTime?` в UTC, `NULL` означает активный таймер)
  - `createdAt`, `updatedAt` (`DateTime` в UTC)

## 11. Бизнес-правила и защита целостности данных

1. **Хранение времени в UTC**: Все временные метки в PostgreSQL сохраняются в UTC, а в интерфейсе отображаются в локальном часовом поясе пользователя.
2. **Защита от повторного и параллельного запуска таймера**:
   - На уровне транзакции проверяется отсутствие активного таймера (`endTime IS NULL`).
   - На уровне PostgreSQL в миграции `20261027000000_init/migration.sql` создан частичный уникальный индекс:
     ```sql
     CREATE UNIQUE INDEX "TimeEntry_one_active_per_employee_idx"
     ON "TimeEntry"("employeeId") WHERE "endTime" IS NULL;
     ```
     Даже при одновременных параллельных HTTP-запросах СУБД гарантированно блокирует создание второй активной записи для одного сотрудника, а API возвращает `409 Conflict`.
3. **Защита от отрицательной длительности**:
   - В таблице `"TimeEntry"` действует ограничение `CHECK ("endTime" IS NULL OR "endTime" >= "startTime")`, а функции расчёта длительности используют `Math.max(0, ...)`.
4. **Сохранение истории при деактивации**:
   - Сотрудники не удаляются каскадно вместе с историей (`ON DELETE RESTRICT`), а переводятся в состояние `isActive = false`. Деактивированный сотрудник не может запустить новый таймер, но его прошлые записи остаются в журнале и отчётах.
5. **Расчёт отчётов по полуоткрытому интервалу `[periodStart, periodEnd)`**:
   - Для каждой записи, пересекающейся с выбранным периодом, вычисляется:
     - `effectiveStart = max(startTime, periodStart)`
     - `effectiveEnd = min(endTime ?? now, periodEnd)`
     - `duration = max(0, effectiveEnd - effectiveStart)`
   - Благодаря этому задачи, переходящие через полночь или границы выбранного периода, учитываются строго в пределах выбранного диапазона.

## 13. Найденные и исправленные ошибки

В ходе разработки и тестирования были обнаружены и устранены следующие ошибки:

1. **Ошибка типизации `z.ZodType<T>` в `strict`-режиме TypeScript для схем с `.transform()`**:
   - *Проблема*: При запуске `npm run build` компилятор TypeScript выдал ошибку в `src/lib/services.ts:416`: тип `timeEntriesQuerySchema` (где строковые query-параметры `activeOnly`, `limit`, `tzOffset` преобразуются через `.transform()` в `boolean` и `number`) не подходил к параметру `schema: z.ZodType<T>`, так как `z.ZodType<T>` по умолчанию требует совпадения входного (`Input`) и выходного (`Output`) типов.
   - *Исправление*: В `src/lib/validation.ts` сигнатура обёртки изменена на `validateWithZod<T>(schema: z.ZodType<T, z.ZodTypeDef, unknown>, input: unknown): T`.
2. **Пробел в имени зависимости в `package.json`**:
   - *Проблема*: При формировании `package.json` пакет `" tailwindcss-animate"` был записан с ведущим пробелом в ключе JSON, что приводило бы к ошибке валидации имени пакета в `npm install`.
   - *Исправление*: Ключ исправлен на `"tailwindcss-animate"` до установки пакетов.
2. **Пограничный случай нулевой длительности при мгновенной остановке таймера**:
   - *Проблема*: В быстрых автоматизированных тестах между `startTimer` и `stopTimer` могло пройти менее `1 мс`, из-за чего `startTime` и `endTime` совпадали (`durationMs = 0`), и запись отфильтровывалась из отчёта за период (`clampedMs <= 0`).
   - *Исправление*: В `stopTimer` (`src/lib/services.ts`) добавлена нижняя граница `const safeEndMs = Math.max(Date.now(), targetEntry.startTime.getTime() + 1)`, что гарантирует положительную длительность (`>= 1 мс`) для любой завершённой задачи.
3. **Окончания строк CRLF в `docker-entrypoint.sh` на Windows**:
   - *Проблема*: При сборке Docker-образа на ОС Windows скрипт `docker-entrypoint.sh` с окончаниями строк `CRLF` (`\r\n`) внутри Linux-контейнера (`node:20-alpine`) вызывает ошибку запуска шебанга `#!/bin/sh\r`.
   - *Исправление*: Добавлен файл `.gitattributes` (`*.sh text eol=lf`) и команда нормализации `RUN sed -i 's/\r$//' ./docker-entrypoint.sh && chmod +x ./docker-entrypoint.sh` непосредственно в `Dockerfile`.
4. **Сбой запуска Docker Desktop из-за битого WSL-дистрибутива по умолчанию в локальном окружении**:
   - *Проблема*: Команда `docker ps` возвращала ошибку подключения к pipe, так как дистрибутив WSL по умолчанию (`Ubuntu`) ссылался на отсутствующий виртуальный диск `ext4.vhdx`.
   - *Исправление*: Выполнено переключение рабочего дистрибутива `wsl --set-default docker-desktop` и перезапуск службы Docker Desktop, после чего контейнеры PostgreSQL и тесты успешно запустились.

## 14. Известные ограничения

- В соответствии с условиями тестового задания в приложении отсутствуют аутентификация, авторизация и ролевая модель (все пользователи работают в едином рабочем пространстве компании).
- Ручное редактирование исторических интервалов времени (`startTime` / `endTime`) через UI не предусмотрено: время фиксируется строго по факту запуска и остановки таймера сервером.
- Экспорт отчётов в файлы (CSV / XLSX / PDF) не входит в рамки текущего MVP.
